Lemma documentation

Architecture baseline

Status: architecture baseline; Task 001 implementation evidence is recorded separately.

Layers

Lean source -> checked Core0 -> LLVM -> RV64 ELF -> LemmaVM establishes the first execution path. A managed Lean runtime is constructed afterward. Above it sit the capability kernel, services, durable store, ink/document system, mathematical checkers, semantic textbooks, learner state and permissioned tutor.

Core0 is an explicitly checked freestanding fragment, not all Lean programs. Managed Lean supplies allocation, object representations and library services only after those implementations exist on the device. Host Lean running the compiler is not the device runtime.

LemmaVM is a versioned machine contract, initially backed by a pinned QEMU RISC-V virt configuration. The final privilege design is M -> S -> U with Sv39. The first smoke image remains in machine mode. User isolation is a Stage II claim.

Lemma One targets a custom monolithic open RV64 mixed-signal SoC, with inspectable compute, memory, pen and paper-controller boundaries. Task005's lemma-silicon-dev/0.1.0 is a digital development binding within permanent LemmaSim; external simulation memory, medium and panel models are explicit. The silicon specification governs this direction. IHP SG13G2 is provisional. Historical board/cartridge and supplier discussions are history, not the active integration dependency. Physical memory, sensing, panel compatibility and whole-chip closure remain unverified.

Target-language boundary

Application, OS, runtime, project compiler and checker implementations are maintained in Lean. A small audited generator may emit machine primitives/startup/LLVM artifacts. Declarations must not merely wrap hand-authored programs in another language. Build tools are allowed to be implemented upstream in other languages on the host; all target inputs and generated code must have an explicit origin.

Authority and evidence boundaries

  • Kernel capabilities enforce access; typed handles alone are not authority.
  • Raw ink, proposed interpretation, verification result and learner estimate are separate.
  • The proof kernel is not the operating-system kernel.
  • Tutor outputs and recognition results are untrusted proposals.
  • Correctness evidence binds the exact goal, domain, assumptions, submission, environment, checker version and resource outcome.
  • Storage commits have a specified failure model; saving to a software queue is not durability.
  • Virtual display timing is a model. Pen-to-visible-ink latency needs physical measurement.

What is deliberately not frozen

Task 001 freezes only the tested scalar profile and its Lean 4.34.1 / LLVM 20.1.8 / QEMU 11.1.1 toolchain. A complete Core0 feature set, managed Lean ABI, physical board firmware closure, peripheral ISAs, screen connectors, waveforms, FPGA resources, and native network cryptography remain unfrozen. See docs/audits/core0-lowering.html for the exact accepted semantics and docs/audits/qemu-core0.html for the machine handoff.

Third-party reference points

Lean's runtime ABI and upstream LLVM emitter are inputs to the audit, not evidence of freestanding readiness. QEMU's firmware selection and RISC-V's psABI are inputs to the virtual platform contract. See docs/SOURCES.html for official references.

First-class LemmaSim decision (2026-10-09)

Lemma One is one specified machine with two embodiments: permanent user-facing LemmaSim and physical Lemma One. The canonical intended machine contract lives in ../LEMMA_MACHINE_CONTRACT.md; the existing LemmaVM document remains the tested historical boot-profile contract. The full virtual hardware, including pen and e-paper controllers, storage, reset and device error behavior, is a foundational parallel workstream. The guest executes the actual Lean-authored software through genuine device interfaces rather than host-side software substitutes. Student, Developer and Laboratory modes share those guest interfaces. Simulator completion requires conformance evidence; physical equivalence requires physical measurements and hardware testing. See plan/LEMMASIM.md.
