# SHA-256 and HMAC-SHA-256 physical-memory substrate1

`lemma-sha256-physical/1` and `lemma-hmac256-physical/1` are ordinary Lean
algorithms using the existing checked `core0-boot-v0.1` lowering. They add no
language feature, intrinsic, allocator or foreign target runtime. The
freestanding component is separate from product image authentication.

The algorithms follow [FIPS180-4, August2015, sections4–6](https://csrc.nist.gov/files/pubs/fips/180-4/final/docs/fips180-4.pdf)
and [RFC2104, February1997](https://www.rfc-editor.org/rfc/rfc2104).
[RFC4231, December2005](https://www.rfc-editor.org/rfc/rfc4231) supplies independent
short- and long-key HMAC vectors. These are pinned publication editions; this
does not claim FIPS cryptographic-module validation or physical side-channel
qualification. The direct PDF byte fetch was unavailable; no reference-file
hash or vendored specification is asserted.

SHA accepts a private1024-byte, eight-byte-aligned workspace in physical RAM
`[0x80000000,0x88000000)`. Its state layout is:

| Offset | Contents |
| --- | --- |
| 0–63 | Eight hash words, each in the low32 bits of a64-bit slot |
| 64–127 | Eight working words |
| 128–639 | Sixty-four message-schedule words |
| 640 | Total input bytes |
| 648 | Pending bytes, equal to total modulo64 |
| 656–719 | Pending block |
| 720 | Active-stream phase marker |
| 728–1023 | Reserved, never authoritative |

`begin` initializes the state. `update` accepts at most4096 bytes per call,
including unaligned spans, and processes full blocks without retaining caller
references. Total admitted input is at most64MiB. `finish` applies big-endian
SHA padding and writes exactly32 digest bytes; it consumes the stream before
padding. Repeated finalization fails. The one-shot `hash` has the same4096-byte
bound; larger images use repeated updates.

HMAC owns2048 bytes. It uses SHA's context at0, an inner digest at1024, a
64-byte padded key at1088 and its phase marker at1200. Keys of at most4096
bytes are supported; keys longer than64 bytes are hashed first. The inner
prefix counts toward SHA's64MiB bound. The full32-byte tag is returned.
Keys come from the caller. No production key, entropy, immutable trust state,
anti-rollback rule or authentication-success constant is supplied here.

Public span/alignment/alias checks precede private mutation. Source and output
must be disjoint from the complete workspace; source/output may alias each
other because output is written after all input is consumed. Streaming data
must remain immutable during each call. The context is private trusted scratch,
not a transferable validation token. Errors248/249/250 mean invalid argument,
resource bound and invalid stream state. Existing physical-access errors
propagate. A library span check does not enlarge the selected compiler profile's physical regions; an otherwise well-formed call outside an admitted region
still fails through the compiled physical primitive. Faults may leave private state or output partially written; callers
must reject the result and initialize before retry. No durable effect occurs.

`Lemma.Crypto.Probe` prints actual computed digests from a freestanding RV64
workload. `scripts/check_crypto.py` independently compares UART bytes with
host-only SHA/HMAC oracles after genuine elaboration, checked lowering, LLVM,
direct-call/stack/runtime/ISA/ELF audits. The host oracle never supplies a digest
to the target. Product ROM selection must still explicitly verify tags before
handoff and preserve authenticated fallback/recovery; these component checks
alone cannot establish that behavior.
