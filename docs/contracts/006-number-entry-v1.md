# Bounded mathematical number entry, version 1

This additive Notebook12 software path uses the unchanged canonical
`lemma-silicon-dev/0.3.0` machine and User2 language profile. The historical
Notebook11 roots and artifact authority remain available. The current canonical
package deployment selects `Notebook.mainPackageNumberPad`; the companion
recovery root retains its existing implementation until separately integrated.

While a course is open, the existing N/D/P0/P1/P2 selectors choose a typed field.
The admitted selected-field values remain0 (default numerator) or the existing
byte offsets56/64/72/80/88; no new selection encoding is introduced. The guest draws a keypad at [448,832) × [160,360). Its header declares TYPE0-99.
Keys1..9 occupy three rows, then CLR/0/BACK. Each key occupies128×40 pixels,
starting at y200. The header is inert. Existing toolbar/course controls retain
their coordinates. A contact already held, discontinuous sequence/epoch/time,
input cancellation, an active stroke, queued raw chunk or failed Save follows
the existing guards before any key can be admitted. Outside the active course,
the region remains ordinary raw ink.

Appending a digit, clearing, or backspacing changes only the selected bounded
nonnegative integer0..99. An unchanged value creates no revision or Save.
Appending above99 leaves all document bytes unchanged and shows LIMIT 99.
Invalid field/key/value rejects before mutation. A real change calls the
existing revision operation exactly once, clearing current evidence and
execution applicability while preserving all attempt/learner-event history.
Revision exhaustion rejects before mutation. Entering denominator zero remains
an editable typed object; the checker must reject division by zero. No raw ink
is reinterpreted and the selected original goal cannot change through a key.

Editing occurs first in the existing private staging document. The existing
PackageWorkspace transition and applicable source/edition/node capture bind the
new revision. The ordinary Store append/BARRIER path publishes the wrapper;
RAM validation or framebuffer completion never produces Saved. Pending/failed
Save behavior is unchanged. The transient keypad words at packageState+184/+192
are private presentation state, outside Doc8 and its durable envelope. They
participate in machine snapshots as ordinary RAM. Reset/reopen reconstructs the
keypad from guest course state; no new disk format or host policy is introduced.

The renderer writes only the384×200 Gray4 span, using aligned words and exact
byte edges. A write fault retains the actual completed prefix. A fresh render
reconstructs every pixel; it promises no rollback. Normal display uploads use
the existing dirty-tile queue and real controller transaction sequence.

Component Action tests and independently predicted framebuffer bytes qualify
these local properties. They are separate from genuine checked LLVM/RV64,
whole-image audit, actual guest checking, durable Save/cold reopen, RTL timing
and browser execution. None is implied by this contract.

Notebook15 adds conservative reuse of the static keypad. The existing painted
word at packageState+184 and limit header at+192 are joined by transient raw
overdraw at+200. A key reuses the pad only when it was completely painted, both
old and new limit headers are valid and equal, and overdraw is zero. Malformed
state forces reconstruction. Mathematical publication, checking and Save retain
their ordinary guest paths.

Admission of any new raw stroke marks overdraw once, before stroke creation,
when the private twelve-page package context exists. Active strokes may cross
the keypad regardless of their endpoints. This marker leaves existing visible
ink in place until the next key. A complete pad render and dirty marking clear
it; partial failure does not claim a reconstructed pad. Cold opening and loss
repaint retain their existing full reconstruction. This is transient software
presentation state, not a processor cache or a new durable document field.
