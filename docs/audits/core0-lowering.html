Lemma documentation

Core0 versioned semantics and lowering

This document freezes the deliberately small profile implemented for Task 001. It describes executable behavior, not a proof that the compiler preserves that behavior. The independent model is Lemma/Core0/Semantics.lean; finite differential tests are evidence only.

Source and checking boundary

The input is an ordinary, safe, monomorphic Lean declaration already installed in a Lean.Environment by the Lean elaborator. Lemma.Core0.checkAndLower reads the kernel-checked ConstantInfo, checks the declaration body, and follows every reachable direct user call. It produces a dependency-first typed Core0 tree. It does not accept surface syntax or a caller-built demonstration AST.

Runtime parameters and results are exactly Bool, UInt8, UInt32, or UInt64. Function parameters are explicit and scalar. Proofs, implicit parameters, aggregates, boxed data, closures, recursion, loops, exceptions, IO, arbitrary extern, implemented_by, initialization attributes, unsafe/partial/opaque declarations, and unknown terms are rejected. An unused host import is irrelevant because only the reachable declaration graph is traversed.

Each primitive match checks its exact Lean declaration identity, complete scalar signature, and the standard instance/decider expression introduced by elaboration. The generated manifest records every dependency-first function signature and deterministic typed Core0 body, its source-to-LLVM symbol mapping, and stable primitive IDs with resolved Lean identities, signatures, and the pure effect. The closure audit cross-checks that data against the normalized and symbol companion artifacts. A same-named user declaration or custom typeclass instance does not enter the allowlist.

Scalar semantics and LLVM rules

UIntN values are mathematical naturals reduced modulo 2^N. LLVM integer values have the same widths. Bool is a Core0 Boolean and lowers to LLVM i1; it is not the boxed Lean runtime representation.

Core0 operation Source semantics LLVM lowering
integer literal value modulo 2^N i8, i32, or i64 constant
add wrapping addition modulo 2^N plain add
sub wrapping subtraction modulo 2^N plain sub
mul wrapping multiplication modulo 2^N plain mul
and, or, xor fixed-width bitwise operation and, or, xor
equality equal Boolean or equal normalized unsigned value icmp eq
<, <= unsigned comparison icmp ult, icmp ule
widening conversion preserve unsigned value zext
narrowing conversion retain the low target-width bits trunc
let evaluate the pure value, then bind it SSA value/local mapping
conditional evaluate the selected branch both pure, total branches lowered followed by select
direct call first-order call with the checked scalar signature direct call to a generated internal symbol

Eager branch lowering is valid only because this profile is pure, total, recursion-free, and contains no source memory operation. Adding effects or partial operations requires replacing that rule with control flow and versioning this contract.

No source operation is lowered with nsw, nuw, inbounds, alias promises, or fast math. The audit rejects those flags in generated input IR. The pinned optimizer may prove and add nsw/nuw from ranges (notably to bounded harness counters and hexadecimal digits); the post-optimization audit inventories those inferred flags and still rejects inbounds. Division, remainder, shifts, complement, floating point, vectors, atomics, and generic memory access have no Core0 IR constructor and are rejected. This avoids importing accidental LLVM poison or a compiler helper whose behavior was not specified.

Additive Core0 v0.2 scalar and control-flow profile

Task 002 adds core0-v0.2; it does not change the core0-v0.1 rules above. The profile is selected explicitly, recorded in the checked-suite and typed-ABI manifests, and rejected when unknown. The frontend still accepts only the closed, exact primitive identities and signatures recorded by the checker. In addition to all v0.1 scalar operations, v0.2 admits fixed-width complement, left shift, logical right shift, unsigned division, and unsigned remainder for UInt8, UInt32, and UInt64. Signed arithmetic remains unsupported.

For a width w, v0.2 gives the new operations these total source semantics:

Core0 operation Source/model result Pre-optimization LLVM rule
complement low w bits of bitwise complement xor with the all-ones i<w> value
left shift (value << (count % w)) mod 2^w mask the actual count operand with w - 1, then shl
logical right shift value >> (count % w) mask the actual count operand with w - 1, then lshr
unsigned division 0 when divisor is zero; otherwise unsigned quotient branch on divisor; execute udiv only in the nonzero block; merge with zero using phi
unsigned remainder dividend when divisor is zero; otherwise unsigned remainder branch on divisor; execute urem only in the nonzero block; merge with the dividend using phi

The count mask is exact for the supported power-of-two widths. The compiler does not rely on a later select to hide an invalid LLVM shift or division. Its structured lowerer emits basic blocks with one terminator each, explicit predecessor edges, and merge phi nodes. The validator checks labels, terminators, branch targets, predecessor sets, phi incoming labels and types, SSA uniqueness, use-before-definition, dominance, call signatures, and return types before LLVM text is exported. Every source conditional also uses branch-and-merge lowering in this profile, so only the chosen branch executes. LLVM may later fold a safe pure branch back to a select; the audit instead requires that every remaining udiv, urem, shl, and lshr stays within LLVM's operand domain.

The pre-optimization audit rejects source-emitted nsw, nuw, inbounds, exact division, and other unproved promises. It additionally verifies that each division or remainder is dominated by its nonzero-divisor edge, that the zero edge cannot reach the dangerous instruction, and that each shift consumes a mask of the same normalized source count operand. The v0.2 corpus exercises the retained v0.1 operations through this new lowerer as well as the five new operations. These checks and finite executions are not a proof of whole-compiler correctness.

Additive Core0 v0.3 bounded-fold profile

core0-v0.3 retains the complete v0.2 scalar/CFG contract and adds one exact compiler-recognized source identity, Lemma.Core0.Bounded.boundedFoldU32. Its compile-time arguments are a canonical standard Nat literal budget in 0..256 and a direct top-level callback of type UInt32 -> UInt32 -> UInt32. The callback is not a runtime closure: its declaration identity is recorded in checked IR, erased from the runtime arguments, and included as an ordinary transitive checker dependency. Callback helpers therefore receive the same rejection checks, dependency paths, and recursion-cycle checks as other Core0 calls.

The two runtime arguments are a UInt32 iteration count and initial accumulator. For a count within the declared budget, iteration visits indices in ascending order starting at zero and replaces the accumulator with callback index accumulator. Success is the final UInt32 value zero-extended to UInt64. A count above the budget executes no callback and returns the explicit tagged outcome 0x8000000000000000 ||| initial.toUInt64. Since successful values occupy only the low 32 bits, the tag is unambiguous and bits 62 through 32 are reserved as zero. This semantic outcome is not the model's traversal-fuel error and is not a host/QEMU timeout.

The pre-optimization lowering evaluates the runtime count and initial value once, guards the loop with unsigned count <= budget, and branches either to exhaustion or a preheader. The loop header has i32 index and accumulator phis. Its body makes one direct, ABI-checked callback call with (index, accumulator), increments the index with plain wrapping add, and takes one backedge. The exit zero-extends the accumulator; an outcome block merges success and exhaustion as i64. The static maximum ensures every executed increment is far below UInt32 wraparound, but no nuw/nsw flag is asserted. Nested bounded folds reuse the same representation and still introduce no aggregate, array, allocator, function pointer, or recursive iteration call.

The checked model interprets that IR independently and validates the callback signature, budget, and checked dependency before iterating. The artifact audit binds each normalized loop site to its direct callback and budget; checks the guard, preheader/header/body/latch/exit relationships, phi inputs, callback argument order, index increment, success value, and tagged exhaustion edge; and rejects mutation fixtures that alter those facts. The audit combines the optimized LLVM direct-call graph with object .stack_sizes metadata, requires that graph to be acyclic with no self-call, and establishes a worst-case summed frame chain below the declared 64 KiB stack. Separately, retained machine backedges and direct callback calls show that runtime counts drive target loops rather than compiler-side repetition. These checks and bounded differential executions are still not a proof of whole-compiler correctness.

The Lean renderer emits no poison-sensitive disjoint, nuw, or nsw premise. The pinned O2 optimizer may infer or disjoint; the audit inventories every such instruction and accepts only a closed set with a local range proof. In particular, an exhaustion payload must come from an i32-to-i64 zero extension, which cannot overlap the bit-63 tag, and hexadecimal formatting operands must be proven low nibbles, which cannot overlap ASCII 0x30. Any other inferred disjoint form fails closed and the resulting inventory is retained in audit.json.

Machine boundary

Machine effects do not masquerade as source primitives. Separate Lean-authored structured generators provide:

  • _start: establish the fixed 16-byte-aligned stack, preserve a0/a1, clear BSS, record the boot hart ID and DTB pointer, call core0_main, then halt if it returns;
  • core0_io_fence: an explicit fence iorw, iorw around ordered MMIO;
  • bounded 16550 polling and byte output at the layout-declared UART region;
  • aligned volatile reads from the reserved host-injected input region; and
  • fenced 32-bit writes to the SiFive test finisher for success or nonzero failure.

The input record is five little-endian UInt64 words: the first eight bytes are ASCII LEMMA001 and load as 0x313030414d4d454c, followed by the case ID and three root arguments. This wire word is distinct from the case corpus tag. The target root ABI is exactly UInt64 -> UInt64 -> UInt64 -> UInt64. The result frame is LEMMA_CORE0/1\nRESULT:<16-hex-case>:<16-hex-result>\n.

The image deliberately has no global-pointer setup. LLVM receives SmallDataLimit=0, assembly and linking disable relaxation, the linker script collects small-data sections explicitly, and the closure audit rejects gp instructions and R_RISCV_RELAX. Any future small-data or relaxation support must establish gp before use and change this reviewed policy.

All maintained target logic is Lean. The generated LLVM, startup assembly, linker script, objects, and ELF are build artifacts. The only permitted pre-link external edge is LLVM code calling the generated core0_io_fence; the final ELF must have no undefined symbol, dynamic section, interpreter, or relocation.

Deliberate limits

This slice has no heap, managed Lean ABI/runtime, general memory API, exception model, general recursion, user-mode isolation, scheduler, filesystem, or proof of compiler correctness. Passing the corpus establishes one bounded scalar vertical slice and does not complete G1.
