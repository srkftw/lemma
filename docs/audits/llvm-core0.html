Why the flake selects unwrapped Clang

The dev shell deliberately selects llvm.clang-unwrapped. The Nix cc-wrapper at /nix/store/1swlw4m64aq15jmni8gpib9xw4kad33s-clang-wrapper-20.1.8 reads the shell's host hardening policy; NIX_HARDENING_ENABLE includes zerocallusedregs, and its nix-support/add-hardening.sh:182 adds -fzero-call-used-regs=used-gpr. That option is not supported by Clang for the RV64 bare-metal target.

A controlled probe compiled the same minimal LLVM module through the wrapped and unwrapped executables inside the pinned dev shell, with --target=riscv64-unknown-elf -march=rv64imac -mabi=lp64 -ffreestanding -fno-builtin -nostdlib -c. The wrapped compiler exited 1 and produced no object:

Warning: supplying the --target riscv64-unknown-elf != x86_64-unknown-linux-gnu
argument to a nix-wrapped compiler may not work correctly
clang: error: unsupported option '-fzero-call-used-regs=used-gpr' for target
'riscv64-unknown-unknown-elf'

The unwrapped executable exited 0 and produced the object. It remains the same pinned Clang 20.1.8 source revision as LLVM/LLD, but its own realized output, derivation, path, and NAR hash are recorded separately. This avoids importing host C-library paths and host-only hardening flags into target compilation; it does not relax the later ELF/helper-closure audit.

Immutable Lean source audit

All paths in this section are under the immutable source tree /nix/store/1szlhrxfpn9a2xadknnd18ynp2qxcq7h-source.

Normal compiler path and usable boundary

Ordinary Lean source is elaborated into declarations in a Lean.Environment. The normal native compiler then proceeds as follows:

  1. src/Lean/Compiler/Main.lean:19-22 invokes LCNF.main for selected declaration names.
  2. src/Lean/Compiler/LCNF/Main.lean:156-212 filters declarations that need code, calls toDecl, runs base and monomorphization passes, runs impure passes, converts LCNF to Lean.IR, and installs the compiled IR.
  3. src/Lean/Compiler/LCNF/ToDecl.lean:121-180 reads the elaborated declaration from the environment, partially erases types and proofs, eta-expands, expands selected definitions/matchers, and produces LCNF.
  4. src/Lean/Compiler/LCNF/Passes.lean:144-158 makes reset/reuse explicit, runs explicitBoxing, inserts explicitRc, expands reuse, and coalesces reference-count operations before saving impure LCNF.

This establishes that the elaborated Environment/ConstantInfo body is a real front-end boundary, before managed-runtime lowering. It is the boundary chosen for the narrow Task 001 checker: inspect the requested declaration and every reachable runtime declaration body, admit only exact scalar primitive identities/types/effects, and translate the resulting checked Core0 IR. It does not construct a toy AST in place of elaboration and it does not route through C.

Upstream LLVM backend is absent in the pinned Lean binary

src/CMakeLists.txt:82 defaults LLVM to OFF. When enabled, src/CMakeLists.txt:456-508 finds llvm-config, defines LEAN_LLVM, and at lines 479-480 rejects every LLVM major except 19. The locked external toolchain is LLVM 20.1.8. The nixpkgs Lean derivation does not enable this option, and the installed binary confirms that fact:

$ lean --features
[]

src/Lean/Shell.lean:133-136 would print [LLVM] only when Internal.hasLLVMBackend is true. src/Lean/Shell.lean:569-572 shows that lean -b calls initLLVM and then emitLLVM; the spelling of the option is not evidence that the feature exists in a particular build.

Emitter target and ABI assumptions

src/Lean/Compiler/IR/EmitLLVM.lean is not presently an acceptable freestanding RV64 emitter for this slice:

  • Lines 24-36 state that its LLVM CI is dysfunctional, the code is not actually tested, and ABI updates for IO.RealWorld, erased void parameters, and closed-term static initializers remain TODOs.
  • Lines 41-47 hard-code size_t to i64 and C unsigned to i32 while explicitly noting that the target should be instantiated. The emitter creates a module at lines 1640-1646 but does not set an RV64 target triple or data layout.
  • Lines 329-345 map scalar widths directly, but map object, tagged object, erased, and void values to pointers; struct and union lowering panics as “not implemented yet.”
  • Lines 485-488 show that Lean Bool is represented as i8 and converted to an LLVM condition by comparing it against zero.
  • getOrAddFunction at lines 49-61 puts the probe-stack=inline-asm attribute on functions. That policy and any generated probing would need a separate freestanding stack/closure audit.
  • Broad module code generation at lines 1216-1263 and 1611-1616 emits the compiler's module declarations, an initializer, and optionally a hosted main; it is not the Core0 root-and-transitive-dependency allowlist.

The absence of a triple/data layout is independently significant even on RV64, where the current size_t guess happens to be 64 bits. Task 001 requires the triple, LP64 ABI, pointer width, data layout, and ELF attributes to be explicit and audited rather than inferred from the host or patched after an opaque emission step.

Managed representations, boxing, and reference counting

The compiler IR is intentionally coupled to the normal Lean runtime:

  • src/Lean/Compiler/IR/Basic.lean:41-85 defines heap object, tagged scalar pointers, tobject, erased/void values, and stack-returned structs/unions. It also states the runtime assumption that pointer and size_t widths match.
  • IRType.boxed at lines 123-126 maps UInt8/UInt16 to tagged values, but maps UInt32/UInt64/usize through tobject in the general IR model.
  • src/Lean/Compiler/LCNF/ExplicitBoxing.lean:16-46 inserts box/unbox operations and boxed function variants for the interpreter and closures. requiresBoxedVersion includes functions with scalar parameters or results, so a direct scalar function does not imply that the compiled module contains only a scalar entry point.
  • src/Lean/Compiler/LCNF/ExplicitRC.lean:14-27 describes the liveness, ownership, borrowing, increment, and decrement insertion performed by explicitRc.
  • src/include/lean/lean.h:151-225 defines heap-object, constructor, array, string, and closure headers. Lines 334-336 define tagged scalar pointers. Lines 664-700 implement/reference the RC operations, and lines 796-838 allocate and initialize constructors.
  • On a 64-bit target, lean_box_uint64 at lines 3001-3004 always allocates a constructor holding the 64-bit payload. Thus a generated UInt64 boxed wrapper necessarily introduces allocation even if its direct scalar entry point does not.

The emitter contains direct calls or declarations for these runtime-helper classes:

  • allocation/data: lean_alloc_ctor, lean_alloc_closure, constructor get/set/release/tag helpers, closure setters, string constructors;
  • application: the lean_apply_N family and lean_apply_m;
  • boxing: lean_box, numeric and float box/unbox helpers, Nat conversion from unsigned values and decimal strings;
  • ownership: lean_inc*, lean_dec*, lean_is_scalar, lean_is_exclusive, lean_del_object, and persistent-object marking;
  • initialization/hosted IO: lean_initialize, lean_initialize_runtime_module, imported-module initializers, lean_io_mk_world, IO-result inspection/construction/error display, lean_setup_args, task-manager initialization/finalization, and panic helpers.

Representative locations are src/Lean/Compiler/IR/EmitLLVM.lean:133-327,565-634,713-794,850-960,1282-1601. The exact closure depends on the declarations compiled, but an audit cannot infer “runtime-free” merely from a scalar source signature.

Externs, initialization, and the linked runtime bitcode

src/Lean/Compiler/ExternAttr.lean:19-41 permits standard, ad-hoc, inline, and opaque external entries selected by backend. The LLVM emitter's external call path at EmitLLVM.lean:656-686 selects the C extern entry, creates a named external function declaration, and reports inline LLVM as unimplemented. This is a general foreign-call mechanism, not the exact Core0 primitive identity and effect allowlist required by the contract.

At EmitLLVM.lean:1619-1676, upstream emission always locates installed lean.h.bc, parses it, links it into the output module, marks its defined globals/functions internal, verifies the combined module, and writes bitcode. src/runtime/CMakeLists.txt:72-94 explains how that bitcode is generated by turning the inline definitions in lean.h into Clang LLVM bitcode.

That inline bitcode is only part of the normal runtime story. The runtime build at src/runtime/CMakeLists.txt:1-67 includes C++ allocation, objects, threads, mutexes, IO, processes, libuv, OpenSSL, stack overflow handling, and optional mimalloc, and builds static runtime variants. src/runtime/init_module.cpp:22-35 initializes allocation, objects, IO, threads, mutexes, processes, stack overflow handling, and libuv. src/initialize/init.cpp:30-49 initializes the runtime, Init/Std/Lean modules, kernel, library, and constructions subsystems.

Finally, src/Lean/Compiler/FFI.lean:24-61 returns host C include and Lean library linker flags. That is appropriate for the normal hosted toolchain but cannot be reused as a freestanding guest linker contract. Static linkage would not make those dependencies permissible.

Host-only C probe used to inspect normal lowering

For diagnosis only, the pinned compiler's C emitter was asked to emit this ordinary Lean declaration:

def core0Probe (x y : UInt64) : UInt64 :=
  if x < y then (x + y) * 3 else x - y

The command was:

printf '%s\n' \

  nix develop --no-write-lock-file --command \

The generated direct entry point had scalar uint64_t parameters/result and called the primitive helpers lean_uint64_dec_lt, lean_uint64_add, lean_uint64_mul, and lean_uint64_sub. The same file also generated core0Probe___boxed, which called lean_unbox_uint64, lean_dec_ref, and lean_box_uint64, plus a module initializer calling lean_initialize_runtime_module, initialize_Init, IO-result helpers, and RC.

This probe was not compiled into guest code and is not the Task 001 production route. It demonstrates both useful scalar semantics to match and why “Lean can emit a scalar C function” is insufficient evidence of a freestanding runtime closure. Lean-to-C-to-LLVM remains prohibited.

Decision for Task 001

The upstream LLVM emitter is not usable as-is for the freestanding Core0 slice because:

  1. the pinned Lean binary reports no LLVM feature and lean -b fails;
  2. the source backend requires LLVM 19 while the locked project backend is LLVM 20.1.8;
  3. the source itself records untested/stale ABI work;
  4. it does not establish the RV64 triple or data layout;
  5. it admits general C externs and emits managed boxing/RC/allocation, initialization, hosted-main, and task/IO helper paths; and
  6. it unconditionally links upstream Lean runtime bitcode.

Task 001 therefore uses a narrow, Lean-authored, fail-closed lowering from declarations already installed by Lean elaboration in Lean.Environment to a small checked Core0 IR, followed by project-owned LLVM generation and the pinned external LLVM tools. The boundary must retain declaration identity and walk the root's actual transitive target dependencies. Unsupported expression forms, managed representations, allocation, closures, arbitrary externs, initializer effects, and unknown helpers are rejected before LLVM is emitted. Only exact allowlisted scalar primitives may lower to corresponding integer operations.

The normal Lean compiler source above is used as the representation and semantic reference, but neither its C emitter nor its managed LLVM emitter/runtime is a guest dependency. This is a scoped scalar bootstrap route, not a claim that the Lean managed ABI or all of G1 has been ported.

Caveats and follow-up evidence

  • Remote tag lookups were used to associate human-readable release tags with commits. Reproduction is anchored by the fixed Nix source hashes and recorded commits, not by assuming tags can never move.
  • LLVM's monorepo source path was evaluated from nixpkgs but was not retained as an inspected local checkout for this audit. The locked nixpkgs expression fixes its recursive fetchFromGitHub hash, and the realized LLVM/LLD outputs have independent NAR hashes.
  • QEMU's large host closure contains optional UI/device libraries. Those are host dependencies only; the eventual guest manifest must separately show that no such library or upstream runtime is linked into the RV64 ELF.
  • Target support listings do not prove ABI correctness. The implementation evidence must still audit target triple/data layout, ELF class/machine/flags, entry point, load segments, relocations, symbols, linked inputs, LLVM intrinsics/helpers before and after optimization, and QEMU's reset trampoline and generated DTB.
  • No QEMU boot or UART result is asserted by this document.
