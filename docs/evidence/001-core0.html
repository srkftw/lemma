Implemented source profile

Lemma.Core0.checkAndLower reads kernel-checked ConstantInfo bodies already installed in Lean.Environment, follows reachable direct declarations, validates exact primitive identities, complete scalar signatures and expected standard instances, and produces a dependency-first typed Core0 tree. The compiler does not replace elaboration with a caller-built sample AST.

The admitted profile is deliberately narrow:

  • runtime values and results: Bool, UInt8, UInt32, and UInt64;
  • first-order monomorphic definitions, explicit scalar parameters, literals, let, pure conditionals and direct calls;
  • wrapping fixed-width addition, subtraction and multiplication;
  • fixed-width and, or, and xor;
  • equality and unsigned </≤ comparisons;
  • unsigned zero extension and low-bit truncation between the admitted widths; and
  • a separately declared machine boundary for startup, aligned fixed input reads, bounded ordered 16550 UART output, an I/O fence and SiFive-test termination.

The guest root is Lemma.Examples.Core0.Positive.entry : UInt64 -> UInt64 -> UInt64 -> UInt64. It directly calls mix64, uses both branches, performs wrapping arithmetic and bit operations, and truncates to UInt32 before zero extending. Additional elaborated positive checks exercise UInt8, UInt32, Bool, conversions and 11 reference evaluator cases. The actual differential guest corpus exercises the entry root; it does not claim that every positive helper is separately booted.

The checker rejects reachable boxed or heap-backed data, allocation, capturing closures, hosted IO, arbitrary extern, unchecked compiler replacements, custom primitive instances, runtime initialization, partial/general recursion, division, remainder, shifts, complement, exceptions, loops, floating point, vectors, atomics, generic memory operations, unknown expressions and unresolved calls. Unreachable host imports are not rejected merely for existing.

The independent model in Lemma/Core0/Semantics.lean interprets checked Core0. It does not call the LLVM lowering. Its shared boundary is the checked Core0 program, so differential execution checks lowering/code generation without pretending to be a compiler-correctness proof.

Why this compilation route was chosen

The pinned Lean binary reports no LLVM feature, and an actual lean -b probe failed at the disabled LLVM-backend assertion. The audited Lean source defaults that backend off, restricts it to LLVM 19 while this repository pins LLVM 20.1.8, lacks the needed RV64 triple/data-layout contract, admits general C externs, and links managed Lean runtime bitcode with boxing, reference-counting, initialization and hosted helpers.

Task 001 therefore uses the genuine elaborated declaration body as its frontend boundary, then a project-owned Lean checker and narrow Lean LLVM lowering. It does not use Lean-to-C-to-LLVM. Details and immutable upstream source paths are in docs/audits/llvm-core0.md; semantics are frozen in docs/audits/core0-lowering.md.

The generated manifest stores the checked function order, source and LLVM identities, signatures, direct dependencies, deterministic normalized typed bodies, and exact primitive contracts. The closure audit cross-checks it with the normalized companion, pre/post-optimization IR, object symbols and final ELF. Low-level assembly is generated from the small structured instruction ADT in Lemma/Machine/Primitives.lean; there is no maintained target C/C++/Rust/Zig/assembly source and no complete target program hidden in a Lean string.

Runtime input and observed UART output

The image is built before a case fixture is created. Each 40-byte fixture contains five little-endian 64-bit words. Its first eight bytes are ASCII LEMMA001 (4c 45 4d 4d 41 30 30 31), whose little-endian integer value is 0x313030414d4d454c; the remaining words are the case ID and three arguments. QEMU's generic loader places the fixture in the reserved, non-overlapping input region at 0x81000000. The image, stack and fixture regions are separately validated.

The distinct value 0x4c454d4d41303031 is retained as the corpus tag in cases.json; it is neither the wire magic nor a random seed and does not generate the cases. QEMU's actual deterministic seed is 1.

Repeat builds

O0 and O2 were rebuilt into fresh output directories. For each profile, all 14 declared reproducibility artifacts (program.ll, optimized IR, both objects/generators, linker/layout/manifest data, image/map/symbol data and platform DTB/DTS) were byte-identical. Invocation records were deliberately excluded from that byte-identity set: provenance.json retains elapsed durations and command/output paths, build.json and audit.json retain output-directory metadata, and their derived wrapper hashes can therefore differ. Per-case run records and the aggregate check-results.json are also observations of a particular run, not claimed byte-identical build products. The target output directories were clean, but the pinned Lake dependency cache was deliberately reused; the claim is fresh target artifacts, not a from-zero rebuild of the Lean toolchain.

Linked-code closure

Both profiles passed the fail-closed audit. The direct link contains exactly two inputs: startup.o, generated from the structured Lean primitive definition, and program.o, generated from checked Core0 plus the fixed Lean-authored harness. The audit validates their exact generation and link commands, source hashes and object hashes.

The final files are little-endian ELF64 RISC-V, entry _start at 0x80000000, integer LP64 with exact ELF flags 0x0 (soft-float and no RVC), and architecture rv64i2p1_m2p0_zicsr2p0_zifencei2p0_zmmul1p0. Allocated sections are exactly .text, .rodata, and .bss; the GNU stack is non-executable. The final ELF has no undefined symbols, dynamic dependencies, interpreter or relocations. The audit checks the exact pre/post-optimization function closure, direct calls only, no inline assembly, object/final FUNC symbols, object relocations, segments/layout, startup disassembly, stack alignment, BSS clearing, a0/a1 preservation, absence of gp use/relaxation and absence of floating-point/vector instructions.

At O0 the final function symbols are _start, core0_io_fence, both checked user functions and the fixed six-function harness. O2 legitimately inlines the helper and UART-drain functions; the post-optimization manifest/symbol closure accounts for the remaining functions.

The deliberate foreign-runtime regression linked a third object while resolving every symbol and retaining lean_alloc_object plus lemma_forbidden_foreign_runtime. Its fixture and object hashes are 499e190134343c1da7402267df0f3869f3c13c9c9b50791c2f82f7357f34e264 and 6770c4c5ba6821a623f9f7747c99375335840a565ea5a69105c36c885a5b7a31. The audit rejected it for violating the exact two-object provenance contract. A clean undefined-symbol table therefore could not produce PASS by itself.
