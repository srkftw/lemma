## Implemented source profile

`Lemma.Core0.checkAndLower` reads kernel-checked `ConstantInfo` bodies already
installed in `Lean.Environment`, follows reachable direct declarations, validates
exact primitive identities, complete scalar signatures and expected standard
instances, and produces a dependency-first typed Core0 tree. The compiler does not
replace elaboration with a caller-built sample AST.

The admitted profile is deliberately narrow:

- runtime values and results: `Bool`, `UInt8`, `UInt32`, and `UInt64`;
- first-order monomorphic definitions, explicit scalar parameters, literals, `let`,
  pure conditionals and direct calls;
- wrapping fixed-width addition, subtraction and multiplication;
- fixed-width `and`, `or`, and `xor`;
- equality and unsigned `<`/`≤` comparisons;
- unsigned zero extension and low-bit truncation between the admitted widths; and
- a separately declared machine boundary for startup, aligned fixed input reads,
  bounded ordered 16550 UART output, an I/O fence and SiFive-test termination.

The guest root is
`Lemma.Examples.Core0.Positive.entry : UInt64 -> UInt64 -> UInt64 -> UInt64`.
It directly calls `mix64`, uses both branches, performs wrapping arithmetic and bit
operations, and truncates to `UInt32` before zero extending. Additional elaborated
positive checks exercise `UInt8`, `UInt32`, `Bool`, conversions and 11 reference
evaluator cases. The actual differential guest corpus exercises the `entry` root;
it does not claim that every positive helper is separately booted.

The checker rejects reachable boxed or heap-backed data, allocation, capturing
closures, hosted `IO`, arbitrary `extern`, unchecked compiler replacements, custom
primitive instances, runtime initialization, partial/general recursion, division,
remainder, shifts, complement, exceptions, loops, floating point, vectors, atomics,
generic memory operations, unknown expressions and unresolved calls. Unreachable
host imports are not rejected merely for existing.

The independent model in `Lemma/Core0/Semantics.lean` interprets checked Core0. It
does not call the LLVM lowering. Its shared boundary is the checked Core0 program,
so differential execution checks lowering/code generation without pretending to be
a compiler-correctness proof.

## Why this compilation route was chosen

The pinned Lean binary reports no LLVM feature, and an actual `lean -b` probe failed
at the disabled LLVM-backend assertion. The audited Lean source defaults that backend
off, restricts it to LLVM 19 while this repository pins LLVM 20.1.8, lacks the needed
RV64 triple/data-layout contract, admits general C externs, and links managed Lean
runtime bitcode with boxing, reference-counting, initialization and hosted helpers.

Task 001 therefore uses the genuine elaborated declaration body as its frontend
boundary, then a project-owned Lean checker and narrow Lean LLVM lowering. It does
not use Lean-to-C-to-LLVM. Details and immutable upstream source paths are in
`docs/audits/llvm-core0.md`; semantics are frozen in
`docs/audits/core0-lowering.md`.

The generated manifest stores the checked function order, source and LLVM identities,
signatures, direct dependencies, deterministic normalized typed bodies, and exact
primitive contracts. The closure audit cross-checks it with the normalized companion,
pre/post-optimization IR, object symbols and final ELF. Low-level assembly is generated
from the small structured instruction ADT in `Lemma/Machine/Primitives.lean`; there is
no maintained target C/C++/Rust/Zig/assembly source and no complete target program
hidden in a Lean string.
