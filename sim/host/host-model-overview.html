LemmaSim host hardware boundary

lemma_model.c/.h implement only project-owned pen/paper register transitions, FIFO/raw samples, controller target/visible RAM, bounded refresh completion and contact-loss policy. They contain no notebook, brush, document codec or recovery. lemma_qemu.c adapts those transitions to pinned QEMU MMIO, real PLIC lines, virtual-clock timers, graphic console and input callbacks. lemma_durable.c models volatile sector writes and explicit stable flushes through the real block path; it has no guest record parser. These maintained C files are host-only and never an input to any RV64 object/link. Files are GPL-2.0-or-later to integrate with QEMU; upstream QEMU and pinned dependencies retain their existing licenses. The target compiler/kernel/software remain Lean.

Prepare the separate host binary once:

nix-build tooling/lemmasim/qemu.nix -o build/lemmasim/qemu

The derivation uses the existing immutable nixpkgs and QEMU source pins, only riscv64-softmmu, GTK/VNC, and explicit pinned build packages. It preserves the historical pinned QEMU output. Build/install each require the actual executable and named machine; an empty Nix output is an error. Added host inputs are pinned by the existing nixpkgs lock: qemu-qmp0.0.6 (LGPL2-or-later/GPL2-only) for offline configuration and pixman0.46.4 (MIT) for graphic console support. Native launch includes -machine lemmasim-virt -cpu rv64,smrnmi=false,smdbltrp=false -m 128M -smp 1 -bios none -nodefaults -global virtio-mmio.force-legacy=false, an explicitly attached block atbus=virtio-mmio-bus.0, and -rtc base=2026-10-10T00:00:00,clock=vm -seed 0x4c454d4d413031. The maintained launch command lives above this hardware layer; hardware tests do not substitute for a guest notebook.

Properties on QOM typelemma-paper-pen:

  • width/height: runtime screen geometry; default1650×2200.
  • pressure-max: default4095, synthetic/raw capability.
  • raw-input: optional fixed72-byte little-endian raw sample stream, scheduled at guest10MHz ticks through the same controller FIFO.
  • raw-output: new file capturing every external ingress record in that same source schema, including rejected samples. Controller sequence/epoch are separately assigned and observable; capture does not bypass loss.
  • trace-file: optional new file for normalized virtual-time hardware events.
  • read-only device-state: JSON string for pen FIFO/loss/epoch and controller busy/completion plus packed target/visible SHA256 values. Use QMPqom-get on /machine/lemma-hardware; no guest memory modification.
  • read-only storage-state: volatile-sector count/capacity and block write, flush and durable-flush counters, plus the optional one-shot delayed write's actual transport ownership interval. Document sequences remain guest state.

QEMU ordinary pointer events enter its input/replay system and then the modeled FIFO. Mouse pressure is half-range and explicitly Synthetic. No physical pressure input has been exercised. Native display presents the controller's visible RAM; headless screendump uses the same graphic console. Frontend rendering never owns strokes or pages. Standard QMP stop/cont and system_reset are external Developer controls. Whole-machine snapshots are unsupported by this adapter; CPU/RAM-only save state cannot be advertised as a coherent snapshot. Pause drains QEMU's block graph and can flush the volatile sector overlay. It does not simulate power loss. Use a declared device cut or Laboratory whole-process SIGKILL while running to test disappearance of pending writes; do not pause first. Native replay uses QEMU's recorded input; feeding captured raw-output a second time would duplicate ingress. Raw-file sessions preserve their scheduled input as an explicit identity-bound source. See the stable/volatile backend.

Literal host boundary checks are independently specified assertions, including faulty busy/loss source variants that must fail them. Actual QEMU checking observes registers, real PLIC pending lines and virtual-time completion. These are hardware observations, distinct from real compiled guest drivers, notebook persistence, replay acceptance and physical conformance. See the normative device ABI and profile.

The transport replay checker records actual native pointer ingress and compares raw bytes, device events/state, block observations, supplied guest serial output, controller pixels and stable media after a replay breakpoint at the recorded instruction count. A bringup guest with blank pixels passes only that transport scope; notebook ink/edit/recovery acceptance remains necessary. The pinned QEMU record/replay configuration uses shift=3,align=off,sleep=on: its icount_account_warp_timer does not process asynchronous replay events with sleep=off. Record/replay clock and warp inputs belong to the session identity. At the record observation boundary, stop the VM, inspect and save its instruction count, then terminate cleanly with SIGTERM. Replay starts with -S -no-shutdown, installs replay-break at that count and requires the observed count to match. The recorded HOST_SIGNAL shutdown pauses if it reaches that same count before the deferred breakpoint callback. A recorded QMP quit instead forces process exit and can race inspection; it is not this close policy. The checker also replays without a breakpoint to independently exercise the shutdown guard.

Read-only initial boot observations can be exported while the machine starts with -S: QMP pmemsave at 0x10010400, length256 yields the binary descriptor. Its words26/27 give the actual reset DTB address/length for a second pmemsave. The exporter must validate descriptor magic/version/checksum and bounded DTB header/length before reading that region. This captures actual handed boot bytes, without turning a host manifest into guest authority.

Task006 adds a separate matched functional binding, lemma-silicon-fast. The selected sim/profiles/lemma-silicon-dev-*.json generates numerical constants consumed by the QEMU device model. Build the historical0.1 profile with the command above, or select its compatible successor explicitly:

nix-build tooling/lemmasim/qemu.nix --arg siliconProfile ./sim/profiles/lemma-silicon-dev-0.2.0.json -o build/lemmasim/qemu-fast-full

This binding uses the real QEMU RV64 CPU with an explicitly checked RV64IM, M/S/U, Sv39, PMP, Zicsr/Zifencei/Zicntr configuration. It has the selected128MiB RAM, frame-pool DMA confinement, profile geometry, supplied silicon DTB and same freestanding Lean ELF. QEMU's reset ROM handoff and instruction scheduling remain backend-specific. It is an ELF-preload development boot path. A real image-update/recovery boot controller remains unfinished.

lemma_fast_block.c implements a bounded, timer-stepped single-request VirtIO-MMIO split queue instead of asynchronous host block coroutines. Each 100ns step owns one controller transition or an aligned DMA transfer; its 512-byte transfer buffer, descriptor cursor, timer deadline, status and IRQ are snapshot state. Writes change a bounded32768-sector volatile overlay. FLUSH publishes raw sector bytes to the independently opened256MiB backing file and finishes the actual fdatasync barrier before status DMA. No guest records are parsed. Reset cancels a request and retains the external overlay; a new cold process retains only backing-file bytes. QOM /machine/lemma-block, property storage-state, exposes the phase and medium counters. The old lemmasim-virt block graph and historical drain behavior are unchanged.

Exact same-backend snapshots for the matched binding use paused QMP commands lemma-save-machine {filename:...} and lemma-load-machine {filename:...}. They call the pinned QEMU state serializer, including CPU/RAM/timers, plus explicit VMState for pen FIFO/contact/loss, all display buffers and phases, input cursor/queued events, and the entire block-controller/volatile-overlay state. Pausing this binding does not drain or flush storage. Saving uses an exclusive new file and never finishes future work. Loading requires the same medium capacity and SHA256 of the durable base. The supported LemmaSim session wrapper validates implementation/profile/image identities and checksums first, copies the snapshot durable base into an isolated session fork, and then loads that fork. A live external file handle is reopened, not serialized. Direct QMP load is a developer primitive and is not a replacement for that manifest and fork validation. Cross-backend microstate migration is absent.

On /machine/lemma-hardware, virtual-time returns virtual nanoseconds; run-until arms a bounded virtual-time pause. external-event accepts exactly eight unsigned decimal fields: DELIVERY_NS TIME X Y PRESSURE FLAGS TOOL BUTTONS. Delivery time and the admitted sample timestamp are distinct. The4096-entry queue is bounded, rejects backwards admission, and is part of the snapshot. File events precede injected events at equal delivery timestamps. The CPU uses -icount shift=3,align=off,sleep=off; this is deterministic functional pacing, not a real-time RTL speed claim.

Profile0.2 additionally enables virtual-panel-synthetic/1: three digital phases, registered-read intervals, pixel drive dwell, final visible scan, and power sequencing. Accepted immutable target pixels, pending digital panel beats, and retained visible pixels remain separate. The virtual panel publishes visible pixels only at controller completion; reset discards pending panel work. The functional model advances elapsed declared virtual controller clocks; the RTL reference emits individual digital beats. Synthetic programs establish digital sequencing only. Physical panel data, safe voltages, electrophoretic response, and panel compatibility remain unqualified.

Detailed fast traces are optional observer output. trace-limit on lemma-paper-pen and lemma-fast-block accepts1..1,000,000 rows per file; additional rows increment trace-state.omitted without changing controller execution. These observer counters are outside machine state and each isolated restore fork owns new output files. Buffered writes replace per-row flushes for this binding. Historical native tracing retains its prior behavior.

The explicit QEMU qtest accelerator executes no CPU. It may instantiate the matched controller inventory for bounded literal DMA/protocol fixtures; that mode makes no ISA, guest execution, or whole-machine claim. Actual fast guest runs retain the declared CPU admission checks.
